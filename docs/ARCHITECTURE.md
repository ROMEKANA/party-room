# アーキテクチャ

## サーバーとデータ

`server/api.js` が参加、状態取得、操作、履歴、公開バージョンを提供する。認証はタブ単位の接続トークンを使い、同名再入室時は古いトークンを無効にする。`server/game.js` が共通の画面遷移、ホスト権限、ゲームへの操作の振り分けを担当する。画面を移るたびに操作対象のIDが変わる。対戦中は対戦IDと対戦リビジョンも照合する。操作IDを参加者単位で記録して短時間の再送を重複実行しない。

D1の `room` テーブルは単一行で、設定、共通設定、参加者の配列順、現在の画面と対戦をJSONに保存する。`server/store.js` はリビジョンに対する条件付き更新で競合を解決し、結果の保存と状態更新はD1の同一バッチで実行する。入室時と認証済みのルームアクセス時に再接続期限切れを整理する。全員の退出が確定すると対戦と一時状態を破棄し、永続設定を残す。進行中の対戦が破棄された場合は結果を書き込まない。旧ルームで不足しているフィールドは読み込み時に補完し、旧クライアントには進行中のTier表の操作を引き続き受け付ける。

`server/room.js` は現役の在籍者から、ゲーム・モード上限までの参加枠を配列順に求める。ゲーム共通の人数設定は `web/games.js` に置き、モードごとの上限があるゲームは `modeMax` を指定できる。`server/game.js` はルーム更新の中で開始時の参加者を確定し、ID順・表示色を対戦に保存する。退出済みの対戦参加者の情報は、その対戦の同名復帰用に保持し、在籍数・観戦順・次の参加枠から除く。結果画面は対戦時の名簿と次回の参加枠を個別に参照する。D1の列追加は不要で、既存の進行中データは保存済みの名簿から表示色を補う。

`round_history` の既存列をそのまま利用する。JSON内の `gameId` でゲームを識別し、値を持たない旧レコードは `tier` として扱う。Circle & Crossのスナップショットには勝者、経過ラウンド数、参加者ごとの勝数と公開済みの盤面を保存する。期限切れ削除は参加・履歴取得・保存期間変更・結果保存のタイミングで行う。旧Circle & Crossのサイト別D1は、そのサイトで作ったルーム用で、本アプリでは新しい共通ルームで対戦を始める。

Tier表の表示データは `server/visibility.js` と `server/consensus.js` で参加者ごとに制御する。`server/circle.js` は自身の札だけを本人に返し、他の参加者には伏せ札の枚数と公開済みの札だけを返す。

Tier表の開始前の役割指名とプレイヤー順は同じルーム更新で保存する。退出や旧設定の復元時は在籍者を照合し、お題担当が無効ならランダム、親だけが無効なら右隣を補う。対戦開始時は接続中の参加者で役割を決め、開始済みの対戦では保存済みの役割を使う。

## 同期とクライアント

`web/sync.js` を全画面で共有する。入室前は公開版の確認のみ60秒間隔、ロビー・設定・最終結果は約1.4秒間隔、対戦中は約450ms間隔、バックグラウンドは約4.8秒間隔。復帰時はすぐに同期し、失敗時は段階的に間隔を伸ばす。ルームリビジョンと接続中プレイヤーのビットマスクが変わらない場合は、対戦データを再送しない。ゲーム個別のポーリングは設けない。

`web/app.js` が共通の入室・ヘッダー・結果操作を調整する。`web/dialogs.js` は共通メニュー、ゲーム設定、履歴、アップデート情報などを担当する。ルール・対戦履歴・アップデート情報は開いた時点のゲームを表示状態に保持する。履歴の取得時はその範囲をAPIに渡し、省略した従来クライアントには現在の画面の範囲を返す。

## 新しいゲームを追加する

1. `web/games.js` に固定ID・表示名・対応人数（必要に応じてモード別上限）を登録し、ロビー用の画像を設定する。表示名を変えてもIDを維持する。
2. 対戦ルールと参加者別の表示処理をゲーム固有のモジュールに置く。`server/game.js` に開始条件・操作・終了の処理を接続する。ゲーム固有設定は既存のルームJSONから読み込み、旧データの既定値を定義する。
3. 共通画面からゲーム設定とプレイ画面を呼び出す。画面遷移と通信は共通の状態同期を使う。
4. `server/history.js` と `web/history.js` にスナップショットと詳細表示を追加する。過去レコードが読み込めることを確認する。
5. 回帰テスト、スマートフォン縦画面の確認、アップデート情報の更新を行う。

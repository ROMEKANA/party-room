# 公開とアップデート情報

## アプリバージョン

| 変更内容 | 更新する番号 | 例 |
|---|---|---|
| ゲーム追加 | 第1番号 | 2.x.x → 3.0.0 |
| 既存ゲームのモード追加・アプリ全体の共通機能追加 | 第2番号 | 2.0.0 → 2.1.0 |
| その他の変更・修正・お題追加 | 第3番号 | 2.1.0 → 2.1.1 |

同時に複数種類の変更を公開する場合は、該当する最も上位の桁を1つ上げ、その右側の桁をすべて0に戻す。アプリ全体で1つのバージョンを使う。`web/version.js` の `VERSION` を全画面、状態同期API、公開版の確認、最新のアップデート情報で共用する。

開発資料やバックアップ運用だけの変更は、SitesのソースとGitHubに反映する。アプリバージョンとアップデート情報を維持し、本番の再公開は省略する。

## アップデート情報

- 画面上の名称は「アップデート情報」。`web/release-data.js` にバージョン、タイトル、変更項目の `description` と `gameIds` を登録する。番号の更新前に、従来の `VERSION` 参照の項目を元の番号に固定する。過去の正式リリース番号と変更内容、見出しだけの旧項目を保持する。公開日が分かる場合は `releasedAt` を記録できる。
- 名前入力画面とロビーでは全件を表示する。ゲーム内では `web/games.js` の該当IDを含む項目だけを表示し、絞り込み後に空になるリリースは省く。Tier表に引き継いだ見出しのみの旧項目は表示する。複数ゲームに関係する項目には該当IDをすべて登録し、共通システムだけの項目には `gameIds: []` を指定する。
- 利用者向けには実際に公開する変更を簡潔に書き、ゲーム・モード名には画面上の正式名称を使う。公開日が不明な過去項目は日付を省略する。検証の詳細は作業報告に記載する。

## 本番公開

1. [テスト方針と回帰項目](TEST_POLICY.md) に従って検証する。回帰不具合が見つかった場合は修正して再検証する。
2. 既存の対戦・設定・履歴とD1データへの影響を確認し、進行中の対戦では旧クライアントとの互換性をできる限り保つ。互換性のない変更は本番ルームで対戦していない時間帯に反映する。
3. 実装と回帰テストが完了したら、依頼で公開を保留している場合を除き、追加確認なしで既存の [Sites本番](https://party-room-to.plushmarshmallow.chatgpt.site) に公開する。公開物はビルド済みWorkerと配信アセット。開発資料はソースリポジトリ内で管理する。
4. Sitesのデプロイ成功と、公開URLの `/api/version` および画面のバージョンを確認する。その後、GitHubバックアップを行う。
5. 復旧が必要な場合は、直前の正常なデプロイ済みバージョンの再デプロイを検討する。DBの変更を伴った場合は、旧バージョンで現在のスキーマとデータを読み書きできるか確認してから戻す。

## GitHubバックアップ

- Sitesを開発と本番公開の主体とする。GitHubはソースコードのバックアップ先とし、毎回同じリポジトリ [ROMEKANA/party-room](https://github.com/ROMEKANA/party-room) の `main` を使う。バックアップのたびにユーザー確認を求める必要はない。
- 本番公開の成功を確認したら、Sitesのデプロイ記録から公開済みコミットを特定し、`web/version.js` のバージョンを確認する。公開版と同一のアプリソースをGitHubへコミット・Pushし、コミットメッセージにバージョン番号と主な変更を記載する。公開コミットをそのまま引き継ぐ場合は、バックアップの内容を記録するコミットでバージョンと主な変更を明記する。
- GitHub側のコミットを読み戻し、配信対象ファイルとビルド設定が公開済みコミットに一致することを確認する。バージョンタグは作成不要。
- 既存のコミットとタグを維持する。強制Pushや履歴の書き換えは禁止。既存のタグが別のコミットを指す場合は、そのタグを保持し、差分の原因を調べる。
- バックアップには再構築に必要なソース、DBスキーマ・マイグレーション、ビルド設定、依存関係と存在するロックファイル、テスト、開発資料を含める。資格情報、シークレット、個人情報、D1の実データ、生成キャッシュ、インストール済み依存パッケージを除外し、引き継ぐGit履歴も確認する。
- 失敗した場合は原因を調査し、公開結果とバックアップ結果を作業報告に記載する。成功時はリポジトリURLとコミットIDを報告する。

## 作業報告

公開URL、アプリバージョン、変更内容、テスト結果、未実施・未確認事項、GitHubバックアップ結果を記載する。DB・互換性に変更がある場合は、進行中の対戦や保存済みデータへの影響を記載する。公開を伴わない作業では、反映先と対応するコミットを示す。

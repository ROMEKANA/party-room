# 公開とアップデート情報

| 変更内容 | 更新する番号 | 例 |
|---|---|---|
| ゲーム追加 | 第1番号 | 2.x.x → 3.0.0 |
| 既存ゲームのモード追加 | 第2番号 | 2.0.0 → 2.1.0 |
| その他の変更・修正・お題追加 | 第3番号 | 2.1.0 → 2.1.1 |

複数の変更があれば最も大きい番号を更新する。全画面・状態同期API・公開版確認のバージョンは `web/version.js` に集約する。

`web/release-data.js` にアップデート情報を追加する。変更ごとに `gameIds` を指定する。空配列は共通システムを表し、名前入力画面とロビーに表示する。1つの変更に複数のIDを登録でき、ゲーム内は自分のゲームIDを含む変更だけを表示する。過去の正式リリースは履歴として保持する。

`npm test` と複数クライアントによる動作確認の後、既存プロジェクトに公開する。データの互換性と、進行中の旧クライアントでの操作を確認する。非互換変更は本番ルームがプレイ中でない時間帯に公開する。必要なら直前のデプロイ済みバージョンを再デプロイできる。

公開物はビルド済みWorkerとその配信アセット。ドキュメントはリポジトリに保存し、Webから直接配信しない。

## GitHubバックアップ

- Sitesを開発と本番公開の主体とする。GitHubはソースコードのバックアップ先とし、毎回同じ非公開リポジトリ [ROMEKANA/party-room](https://github.com/ROMEKANA/party-room) の `main` を使う。バックアップのたびにユーザー確認を求める必要はない。
- 本番公開の成功を確認したら、Sitesのデプロイ記録から公開済みコミットを特定し、`web/version.js` のバージョンを確認する。公開版と同一のアプリソースをGitHubへコミット・Pushし、コミットメッセージにバージョン番号と主な変更を記載する。公開コミットをそのまま引き継ぐ場合は、バックアップの内容を記録するコミットでバージョンと主な変更を明記する。
- 公開版を再現できるコミットに `vX.Y.Z` のGitタグを作成してPushする。GitHub側のコミットとタグを読み戻し、配信対象ファイルとビルド設定が公開済みコミットに一致することを確認する。
- 既存のコミットとタグを維持する。強制Pushや履歴の書き換えは原則禁止。既存のタグが別のコミットを指す場合は、そのタグを保持し、差分の原因を調べる。
- バックアップには再構築に必要なソース、DBスキーマ・マイグレーション、ビルド設定、依存関係と存在するロックファイル、テスト、開発資料を含める。資格情報、シークレット、個人情報、D1の実データ、生成キャッシュ、インストール済み依存パッケージを除外し、引き継ぐGit履歴も確認する。
- 失敗した場合は原因を調査し、公開結果とバックアップ結果を作業報告に記載する。成功時はリポジトリURL、コミットID、タグも報告する。
- バックアップ運用のみを変更する場合は、アプリバージョンと利用者向けアップデート情報を据え置き、運用資料をSitesのソースとGitHubへ反映する。
